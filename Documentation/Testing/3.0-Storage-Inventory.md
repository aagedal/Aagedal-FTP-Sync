## Existing store set

Normal repository defaults use the user-domain Application Support directory
returned by Foundation, then `AagedalFTPSync/`. Sandboxing may place that directory
inside the app container; integration must obtain it from the existing APIs,
never assume a hard-coded home path. Most JSON store names contain a historical
version but do not independently enforce a versioned outer envelope.

The `.backup` suffix in this table is appended to the complete filename.
Inventory recursive directories under writer exclusion, reject symlinks and
special files, and retain every declared absent/present primary and backup.
Unknown related-store paths require review; an enumerated list is not proof that
future writers have not introduced another store.

`AppPersistenceCoordinator.load()` is not a read-only migration source: it can
migrate embedded server profiles, merge photographer libraries, resolve profile
references, and recover individual files. Build a migration adapter before
creating the regular repositories/coordinator. Validate the full converted set,
including job-to-server/profile/calendar references, audit/signature/ownership job
identities, pending-receive source/duplicate identity and calendar/account bindings.
Do not assemble unrelated primary and backup revisions silently; any recovery
selection and its provenance must be explicit and validated together.

## State outside these files

- `KeychainStore` service `no.aagedal.AagedalFTPSync.credentials` retains endpoint
  credential IDs and `metadata-sync-device-<account UUID>` device credentials.
  Do not export/copy credential bytes. Existing credential garbage collection only
  sees current stores; **before enabling v3, prevent deletion of IDs still referenced
  by retained 2.9 stores**, or split ownership explicitly. Keeping files alone does
  not protect their credentials.
- `@AppStorage` keys `metadataSync.serverURL`, `photographerMapRenderingMode`, and
  `photographerMapShows3DBuildings` are settings outside the JSON set. They presently
  contain no template-bearing records. New drafts/processing policies must use the
  v3 namespace. macOS window state, login registration and Sparkle preferences are
  separate OS/framework settings and are not migrated by this primitive.
- Current editor/calendar clipboard values are in-memory/UI state, not a separate
  app persistence file found in this inventory. Explicitly version any persistent
  drafts/clipboard introduced later; the system pasteboard is not a migration store.
- Working images/rollback backups in the temporary directory, visible destination
  outputs and source `.aagedal-sync-*` staging files belong to transfer transactions.
  Quiesce transfers before migration; do not sweep or copy user media into settings
  backups. Current helper neither restarts nor stops jobs.
- The new model installation, people-library snapshot and processing provenance
  stores do not exist in this baseline. Their chosen paths and schemas must remain
  inside the v3 boundary and be added before those features ship.

## Implemented opt-in API

`VersionedAppStorage(root:)` takes an existing, trusted directory. No production
constructor or startup code calls it. `openOrMigrate(plan:convert:validate:)` accepts:

- An explicit relative-file inventory, including optional files that are absent.
  Defaults cap each source/output set at 512 files and 256 MiB. Paths are bounded
  to 1,024 UTF-8 bytes and 16 components; empty/traversing/absolute/duplicate and
  file-as-parent paths are rejected. Callers can deliberately choose different
  count/byte budgets after measuring real stores.
- A converter receiving immutable bytes by relative path and returning the complete
  initial v3 store set. It owns legacy schema decoding, feature-off defaults,
  explicit v3 envelopes and reference repair decisions. No implicit JSON conversion
  is embedded in the filesystem helper.
- A mandatory validator of versioned stores and cross-store references, invoked on
  staged data and every subsequent open. Production validators remain to implement.

The primitive obtains a nonblocking `flock` on `.v3-migration.lock`; a competing
migration cannot enter conversion. This lock serializes cooperating migrations,
**not a running 2.9 app or normal repository writers**. The caller must enforce
writer exclusion and hold it for the entire operation. SQLite files with `.sqlite3`,
`.sqlite` or `.db` names are refused when any adjacent `-wal`, `-shm` or `-journal`
is present. This check is a guard, not proof of quiescence or a substitute for the
SQLite backup API. No database is opened, checkpointed or modified by this helper.

Reads open each relative component with `O_NOFOLLOW`; regular-file type, hard-link
count, byte limits, inode and nanosecond change/modify times are checked. Source
presence, identity and bytes are rechecked after conversion/staging and before the
boundary. This detects observed per-file mutation/new/deleted inputs; it cannot
prove a consistent cross-store transaction or an omitted-directory entry.

Root and ancestors must be trusted and stable throughout. Stable symlinked roots,
parents, files, locks and installation paths are rejected. Filesystem calls that
create/rename paths do not pin every ancestor descriptor, so this primitive does
**not** claim containment against a malicious same-user process swapping ancestor
directories concurrently. Production integration must enforce the trusted stable
root assumption or harden these calls with descriptor-relative writes/renames.

## Transaction and recovery

For each attempt, `.v3-migration-<UUID>/legacy/` receives untouched declared source
bytes. `.v3-migration-<UUID>/install/` receives converted stores. Both share a
version-3 `storage-manifest.json` containing migration identity, original presence,
byte counts and SHA-256, and initial output hashes. The legacy snapshot remains
outside the mutable `v3/` directory after installation, is never subsequently
written by the helper, and is rehashed on each open. It is not an OS-immutable file
flag or a backup of later v3 edits; app-level backup/recovery remains necessary.

Files are created exclusive with mode 0600; directories use 0700. Files and parent
directories are synchronized. The initial boundary JSON is written to a unique
sibling temporary file, synchronized, then published with an exclusive atomic
rename and root synchronization. It contains **PREPARED**, migration UUID and
manifest hash. After this point the helper never rereads legacy stores to retry.

The fully validated `install/` directory is atomically renamed to `v3/` using
`RENAME_EXCL`, so an existing target is never replaced. Both source archive parent
and destination root are synchronized. The boundary then atomically becomes
**COMMITTED**. Every open validates its identity/schema, immutable snapshot and
mandatory current store schemas. Initial output hashes only gate preparation and
interrupted installation: legitimate later v3 saves necessarily change them.

| Observed state | Behavior |
| --- | --- |
| No boundary and no `v3/` | A new attempt may snapshot quiescent legacy files; unselected orphan attempts remain intact |
| PREPARED, no `v3/` | Ordinary open returns `recoveryRequired`; explicit `recoverPreparedInstallation` validates and finishes only that exact frozen stage, regardless of later legacy edits |
| PREPARED, valid `v3/` | Crash occurred after directory installation; verify initial output hashes, then complete the boundary |
| COMMITTED, valid `v3/` | Validate current stores and reopen; never run conversion again |
| COMMITTED, missing `v3/` | Fail with `committedStorageMissing`; never treat original migration data as a current-state backup |
| Malformed boundary, wrong/future manifest, altered snapshot, missing/invalid required store, or unmarked `v3/` | Fail closed; no fallback and no overwrite |

Orphan temporary boundary files and pre-boundary archives are not automatically
selected or deleted. An interruption while writing a temporary marker cannot
publish a partial final boundary. The helper does not yet expose user-facing
recovery messages or a cleanup UI. Fault-injection tests model process interruptions
at defined boundaries; they do not prove physical power-loss/storage-device behavior.
