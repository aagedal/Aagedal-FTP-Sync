# M0 template persistence and shared-calendar contract

Status: proposed implementation contract, 2026-09-09. No runtime behavior or
server deployment is changed by this document. The adjacent JSON fixtures are
design examples, not passing implementation tests. Reviewed source baseline:
`adf995b6adf9eeb77cf49084c903b2ef2adac405`.

## Findings in 2.9.2

- `ScheduledMetadataFields` stores Headline, Description and Keywords as ordinary
  strings; `PhotographerProfile.copyrightNotice` is also an ordinary string.
  Swift Codable ignores unknown keys, so adding an activation flag alone does
  not stop an older binary from writing unresolved template source as metadata.
- `ConfigurationTransfer` accepts payload versions 1–2. Both plaintext and
  encrypted paths validate the inner payload version; the encryption envelope
  has a separate version, currently 1.
- `MetadataCalendarClient` sends `X-Aagedal-Protocol: 2`. `index.php` only routes
  that header to `live.php`; other POST requests can reach hosting checks.
  `live.php` returns protocol 2 and reconstructs an allowlisted document. It
  rejects unknown profile/clip/field keys. That validation must stay intact.
- `snapshot()` supplies documents for reads, create retries, successful writes
  and revision-conflict errors. Checking only normal GET responses would leak
  source through the 409 path.
- `metadata-sync-v1.json` contains binding snapshots, conflicts and a pending
  receipt journal containing source/duplicate jobs. Jobs also retain applied
  calendar content in `jobs-v2.json`. Blocking a server request cannot remove
  content already cached by another binary.
- Field merges currently merge copyright/headline/description/keywords as values.
  `SharedMetadataDocument.init` reconstructs profiles and would drop a newly
  added copyright marker unless deliberately extended.

## Template source and activation

Keep current text properties, and add the following **proposed wire names**:

| Record | Marker | Meaning |
| --- | --- | --- |
| `ScheduledMetadataFields` (inside clip or preset) | `templateVersions`, object mapping `headline`, `description`, `keywords` to integer `1` | The named field is activated in template language 1. Keywords activation covers the complete ordered array. |
| `PhotographerProfile` | `copyrightTemplateVersion: 1` | Copyright is activated in language 1. |

An absent marker means literal text, including braces and escape sequences.
An empty `templateVersions` object normalizes to absence. Null markers, booleans,
zero, unknown field names and unsupported versions are errors, not literal
fallbacks. A marker's presence is the explicit activation decision. Never infer
activation from braces, an app version, a job toggle or a remote capability.

Persist source and activation together. For equality, merge, paste, preset
application, export, selected-day copy and conflict resolution, each pair
`(source, optional language version)` is one atomic value. The whole Keywords
array and its optional version is one value; do not independently merge source
and marker. A local source edit and remote activation of the same field conflict,
even if each individual scalar could be merged without conflict.

Activation requires supported syntax validation. Editor drafts remain in local
draft state, separate from the last committed source/marker pair, and are never
written as metadata or sent to the server. Editing an activated field retains
the last valid pair until the replacement validates. Disabling variable use must
explicitly convert to literal text with a visible preview, or retain the draft
and previous committed pair; never silently strip a marker during import or sync.

Template language 1 is the complete documented 3.0 catalog, including location
and persons variables. A valid but currently unavailable dependency suppresses
the affected field; it does not make the template literal. Machine geocoding,
recognition, model/library and time-zone policies remain outside shared records.
Date-range filtering retains markers on every retained record; unselected records
must not be copied into an exported range. Source text is never replaced by an
editor's resolved sample. Unknown versions block activation/application of that
document while preserving the previous local usable state.

## Local storage and downgrade boundary

Before any 3.0 template can be saved, migrate the complete related store set to
`Application Support/AagedalFTPSync/v3/`. Use a `storage-manifest.json` envelope
with `format`, `version: 3`, migration identity, source hashes and a commit marker.
Each new JSON store must validate its own explicit schema version before records
are decoded. Paths in this section are a design contract, not existing files.

At minimum migrate jobs, photographer library, presets, sync accounts/bindings,
conflict/pending-receive state and metadata audit. Isolate processing provenance,
source-signature and output-ownership/manifests as well when 3.0 begins changing
their semantics. Inventory current primary/backup/journal paths before migration:

- `jobs-v2.json`, `metadata-presets-v1.json`, `photographers-v1.json`
- `metadata-sync-v1.json`, `metadata-audit-v1.json`
- `original-source-signatures-v2.sqlite3`, its SQLite companions and older
  signature migration backups; `download-manifest-v1.json`, `download-names-v1/`
- Any persistent clipboard/draft or receipt stores introduced during development

Close writers and take a consistent snapshot before conversion (use SQLite's
backup mechanism for an open database, not a bare main-file copy). Stage the
entire migration in a sibling temporary directory, validate round trips and
cross-store references, then atomically install `v3/` and its committed manifest.
On interruption, resume/retry from the untouched originals. Once committed, a
missing or invalid v3 store fails closed and offers v3 recovery; do not fall back
to 2.9 stores and silently discard templates. All new features decode off from
legacy source data. Serialize first migration against another instance; do not
copy a changing 2.9 store set.

Keep original 2.9 files and a separate immutable migration backup intact. Never
write template source into their main, backup, journal or cache files. Shared
transport credentials need not be copied into exports; avoid removing credentials
needed by the retained installation. A 2.9 launch uses its old settings and old
literal calendar snapshots. Changes made there do not automatically merge back
into v3. Returning to 2.9 restores the old configuration state, not the new
templates. This does not roll back files already delivered by either version.
Concurrent transfer jobs from both binaries remain an operational conflict;
the migration/recovery UI must make the active-store boundary clear.

## Configuration packages

Use configuration payload version 3 when the selected contents include any
template marker or unsupported 3.0 processing semantics. Keep encryption
envelope version 1 unless cryptography changes independently. Continue importing
versions 1 and 2 with literal text and all new processing defaults off.

Legacy-compatible export is allowed only after an explicit compatibility scan
of the entire selected payload finds no unsupported semantics. In that case
encode an actual v2 shape, omitting new keys, without modifying local records.
Never drop markers to force a v2 export; never substitute resolved sample values.
Test plaintext and encrypted v3 packages with the actual old import path. A
package's schema gate must reject a future version before mutating repositories.
Imported jobs stay disabled and require local setup where appropriate; ordinary
packages exclude model bytes, face thumbnails/embeddings and machine paths.

## Protocol 3 and server storage

Use `X-Aagedal-Protocol: 3` and JSON `capabilities: ["metadata-templates-v1"]` on
every protocol-3 request. `getCapabilities` is an authenticated, read-only action
with no document in either direction. Its response declares protocol 3,
`capabilities`, `documentSchemaVersions: [1, 3]` and
`templateLanguageVersions: [1]`. The client must establish this contract with
the current endpoint before any template-bearing request; a cached successful
probe is insufficient authorization to send to a changed endpoint. Normal v3
requests repeat capabilities and the server rechecks them. A protocol-1 hosting
check response, v2 envelope, unknown capability or HTTP success without the
required declaration does not prove support.

Preserve protocol-2 calendars using their exact legacy document shape and
existing tables. Protocol-3 template calendars occupy **separate v3 calendar,
membership and invitation tables**, never the legacy `aftpsync_calendars` table.
Existing device authentication may be reused, but all calendar authorization and
invitation lookups are namespace-aware. No SQL view or fallback exposes v3
documents through legacy tables. V3 calendar UUIDs cannot collide with legacy
UUIDs, and legacy create must reject a UUID reserved by v3 on an upgraded server.

This physical separation is required because rolling back to the old PHP files
would ignore a new `minimum_protocol` column on the legacy table. A column or
header check alone cannot protect template strings from a server-code downgrade.
With separate tables, rolled-back code cannot see template records. A recreated
legacy UUID after server rollback still cannot modify the distinct v3 table;
re-upgrade must detect/quarantine any namespace collision before serving it.

A v3 calendar snapshot declares `documentSchemaVersion: 3`,
`minimumClientProtocol: 3`, `requiredCapabilities: ["metadata-templates-v1"]`.
These attributes are immutable for that calendar even after all templates are
removed. All v3 document-bearing requests must explicitly supply schema 3;
missing schema/markers are not silently interpreted as a downgrade. The server
validates keys, bounds and syntax/version markers, stores them verbatim, and
preserves them through range reconstruction. Existing byte/count limits remain.

For retained records, an active-to-literal transition in `putCalendar` requires
an explicit matching entry in `templateDeactivations`, with `recordKind`
(`clip` or `photographer`), `recordID`, `field` and `previousVersion`. Compare
against the locked current revision, require the existing `expectedRevision`,
and reject missing/extra transitions as `template_activation_lost`. This makes
accidental marker stripping detectably different from a user conversion. Whole
record deletion remains normal deletion; new literal records need no transition.
The list does not bypass membership, range, validation or revision checks.

For a known v3 calendar an upgraded server returns HTTP 426,
`client_upgrade_required`, to a protocol-2 request or a protocol-3 request lacking
the required capability. **No calendar or document is included.** Perform this
gate after authentication/authorization but before snapshot construction,
revision comparison or mutation, including idempotent create retries, invitation
acceptance and 409 conflict responses. Unauthorized callers retain generic
access-denied responses. Protocol-2 listings omit v3 calendars; protocol-3 listings
include compatibility summaries without inline documents. Old clients continue
to share legacy calendars normally.

Capabilities describe client ability; they are not a security boundary against
a deliberately modified client claiming support. The enforced contract prevents
accidental exposure to supported old binaries and server rollback paths.

## Upgrading an existing shared calendar and offline safety

Do not activate templates in place in a protocol-2 calendar. The UI offers
**Create template-enabled calendar** after capability verification. This creates
a new v3 calendar identity from a validated current literal snapshot. Record the
source calendar ID/revision locally for provenance. Review unsynced edits first;
do not silently resolve them during conversion. The old calendar remains a
separate literal calendar. Explain that participants must use 3.0 and join the
new calendar, and that subsequent changes are not mirrored to the old calendar.

Creation is idempotent on a persisted new UUID. Write a v3 local migration journal
before sending; on uncertain response, fetch that same UUID instead of creating
another. Switch the selected local job binding only after server success and
durable save of the new snapshot; retain the old baseline for recovery. Start
the new calendar with only the owner's membership. Do not silently copy old
invitations or credentials into new access grants. Existing invitation controls
can explicitly invite supported clients using fresh v3-scoped tokens.

An offline 2.9 client can only hold the old literal snapshot, because neither
server nor local migration ever wrote template-bearing data to its namespace.
When it reconnects, its queued update targets the old calendar ID and cannot
overwrite the v3 document. If it guesses/receives a v3 ID, its read/write/conflict
request is rejected without a document. An offline 3.0 client uses only its v3
cache and retains activation while merging against an immutable baseline.

There is no retroactive repair guarantee for experimental deployments that
already leaked activated source into legacy caches. Such calendars must be
flagged during migration and excluded from this safety claim until affected
devices/caches are inventoried and recovered. A server rejection cannot prove
those old copies are gone. Legitimate old literal text containing braces is not
evidence of a leak and must stay literal.

## Deployment and implementation integration

1. Implement and test separate v3 schema, dual routing and capability enforcement
   in disposable MySQL/PHP first. Keep old routing and validation behavior.
2. Install the upgraded server before enabling shared variables. Deployment to
   a production host is outside autonomous implementation authorization.
3. Ship v3 local storage migration, package v3 and client capability checks.
   An old server remains usable for literal sharing. On an old-server binding,
   offer local templates only through a detached copy or new local job; never
   insert them into that binding's publication document.
4. Create/join the new shared calendar explicitly through the app workflow.
   Never automatically downgrade its namespace or issue a v2 retry containing
   template data after a v3 error.

Integration points:

| File/component | Required change |
| --- | --- |
| `Models/MetadataAutomation.swift`, `MetadataPreset.swift` | Marker decoding/validation, atomic copy semantics, no legacy brace activation |
| `Models/SharedMetadataCalendar.swift` | Preserve profile/field markers; envelope gate; range copies; keep independent processing settings when schedule becomes empty |
| `Models/MetadataCalendarMerge.swift` and conflict view | Compare/display source with activation as one conflict value |
| `Persistence/ConfigurationTransfer.swift` and coordinator | v3 inner payload, semantic compatibility scan, old imports off, disabled imported jobs |
| Job/preset/photographer/audit repositories and startup | Complete staged v3 migration and recovery manifest |
| `Sync/MetadataCalendarCoordinator.swift` | Versioned cache and pending journals; namespace-aware bindings; no automatic literal retry; create-and-rebind workflow |
| `Sync/MetadataCalendarClient.swift` | Probe, request capability, envelope-before-document validation, typed upgrade errors |
| `Server/MetadataSync/public/index.php`, `live.php`, SQL schema/tests | Dual routing, v3 tables, enforce before every response/mutation, preserve allowlist and transaction serialization |
| Editor/clipboard/selected-day/preset paths | Retain marker/source pairs; keep invalid drafts out of publication |

## Required implementation tests (all pending)

The fixture directory uses wrapper keys `request`, `response`, `expected` to
describe a scenario; only nested request bodies are wire payloads. Authentication
headers/credentials are intentionally omitted. The JSON syntax can be validated
without an app, but that is not evidence that any protocol behavior passes.

- Decode 2.9 fixtures with literal braces and escaping-looking text, upgrade/save,
  and demonstrate no activation, including offline bindings and pending receipt.
- Per-field activation through preset/copy/selected day/import/full export and
  conflicting source-versus-marker edits; unknown/null/future versions reject.
- Real 2.9 package reader rejects plaintext and encrypted v3 without changes;
  semantic-free v2 export remains accepted and round-trips literally.
- Crash at every local migration and create/rebind journal boundary; no partial
  cross-store migration or silent fallback; reopening 2.9 sees retained settings.
- Protocol 2 legacy create/get/put/list/invite/conflict still work. Test actual
  serialized 2.9 request payloads, not only synthetic modern request structs.
- Protocol 2 request for v3 ID, missing v3 capability, stale-revision v2 write,
  create retry, invitation replay and date-range access disclose no document and
  leave revision/content unchanged. Verify bodies, not just status codes.
- Server rollback to original PHP cannot read v3 rows. Re-upgrade preserves
  source, markers and revision; namespace collisions fail closed.
- Offline v2 edit reconnects to its original literal calendar; v3 snapshot remains
  byte/semantically unchanged. Offline v3 merges preserve source/activation pairs.
- Missing schema, marker stripping without an explicit user literal conversion,
  malformed template and unknown version are rejected before save/publication.
- Provider/model/library/time-zone machine policies and private library contents
  never appear in shared documents, ordinary packages or support logs.

M0 completion here means a concrete reviewed contract and fixtures exist. M3
completion requires runtime implementation plus these observed tests; neither
the contract nor well-formed example JSON satisfies that gate.
