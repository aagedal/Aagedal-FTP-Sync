# Aagedal FTP Sync 2.7 Improvement Plan

This plan tracks the highest-impact follow-up work from the September 2026 app review. Correctness and recoverability come before performance and structural cleanup.

## P0 — Metadata timestamp correctness

Goal: never rewrite metadata using a timestamp policy that could not be evaluated from authoritative data.

- [x] Propagate source connection and listing failures during metadata reprocessing instead of silently treating the source as empty.
- [x] When source modification dates were not preserved at the destination, refuse to reprocess files that no longer have a matching source entry.
- [x] Add regression coverage for an unavailable source and for missing source timestamps with date preservation disabled.

Acceptance criteria:

- Reprocessing performs no writes when it cannot obtain required source modification dates.
- The user receives an actionable error explaining how to reconnect the source or use camera-capture scheduling.
- Reprocessing remains available for preserved-date destinations whose originals have already been moved to the processed folder.

## P0 — Durable job mutations

Goal: the in-memory job list, persisted jobs file, Keychain credentials, and per-job history must not contradict one another after a write failure.

- [x] Persist add, quick-edit, enable/disable, start-all, stop-all, and delete mutations before publishing them in memory.
- [x] Delete credentials and per-job histories only after the jobs file has durably recorded the deletion.
- [x] Report persistence failures without changing scheduling state.
- [x] Add failure-injection tests for add, toggle, and delete operations.

Acceptance criteria:

- A failed jobs-file write leaves the visible and scheduled job state unchanged.
- A failed deletion leaves the job and its dependent state intact.
- Successful behavior and existing menu-bar controls remain unchanged.

## P0 — Recoverable processed-source removal

Goal: a failure while deleting staged source files must not strand originals under hidden `.aagedal-sync-*.hold` names.

- [x] On a deletion failure, restore every holding item that still exists and report any items that were already deleted.
- [x] Preserve the existing all-or-nothing rollback when staging itself fails.
- [x] Add transport-independent tests for first- and later-item deletion failures.

Acceptance criteria:

- No undeleted holding item remains hidden after a recoverable failure.
- Error messages distinguish fully restored items from items already removed after verified processed copies were published.

## P1 — Release workflow

- [x] Correct the Xcode project path in the security script, README, and security documentation.
- [x] Run the security baseline, vendored SSH signature tests, and application test suite from the documented commands.

## P1 — Delivery latency and resource control

- [x] Design a collision-safe replacement for the currently unused fast-start listing path. See `2.7-Delivery-Latency-Design.md`.
- [x] Add a global sync concurrency limit and optional per-host throttling.
- [x] Benchmark first-file latency and full scan time on large FTP/SFTP trees. See `2.7-Delivery-Latency-Benchmark.md`.

## P2 — Product and maintainability

- [x] Keep metadata preview read-only when managed output folders do not yet exist.
- [x] Split scheduling, persistence coordination, and configuration transfer out of `AppStore`.
- [x] Split timeline editing, preview, and reprocessing coordination out of `MetadataProgrammingView`.

## Remaining 2.7 release scope

The following work extends the original plan with the findings from the final pre-release application review. The ordering favors truthful reporting and recoverability, then unattended operation, delivery latency, and maintainability.

### P0 — Truthful partial-run reporting

Goal: completed work must remain visible when a later file or cleanup step fails.

- [x] Return completed transfer, processed-file, cleanup, conflict, and metadata-audit results with a run failure.
- [x] Persist partial transfer totals and metadata audit entries before publishing the failed phase.
- [x] Include a concise partial-success summary in the visible error and persistent error history.
- [x] Make primary-file and companion-sidecar destination publication one atomic output group.
- [x] Add regression coverage for a later-file failure, a processed-file failure after destination publication, and a cleanup failure after transfers.

Acceptance criteria:

- A run that publishes files before failing never reports zero completed work.
- Metadata audit entries for completed output groups survive the failure.
- A partially published primary/sidecar group is either completed or rolled back.
- Cancellation remains cancellation and is not recorded as a failed partial run.

### P0 — Transactional credentials and job persistence

Goal: the jobs file and Keychain must always agree about which credential a saved endpoint uses.

- [x] Stage password changes under fresh credential identifiers.
- [x] Commit the job reference before deleting superseded credentials.
- [x] Remove staged credentials if the jobs-file commit fails.
- [x] Define and test explicit saved-password removal.
- [x] Surface Keychain read errors in the editor instead of silently showing an empty password.

Acceptance criteria:

- A failed job save cannot change the password used by the previously saved job.
- A failure saving either endpoint password leaves both previously saved credentials usable.
- Users can deliberately clear a stored password.

### P1 — Companion-aware cleanup

Goal: cleanup treats a camera RAW file and its XMP sidecar as one logical output.

- [x] Discover generated and existing XMP companions for cleanup candidates.
- [x] Re-check the age and type of the whole output group immediately before deletion.
- [x] Delete or restore the group transactionally.
- [x] Add RAW-filter and All Photos regression coverage.

### P1 — Source-signature lifecycle and storage

Goal: signature state stays bounded and does not amplify writes on large metadata runs.

- [x] Remove all source signatures after a job deletion is durably committed.
- [x] Prune signatures belonging to superseded source endpoint identities.
- [x] Replace one-full-file-write-per-image with a batch or journaled persistence design.
- [x] Atomically replace repository backup files instead of deleting the old backup first.

### P1 — Unattended failure visibility

Goal: a menu-bar-only user notices actionable failures without opening every job.

- [x] Add a failed/warning state to the menu-bar icon and accessibility label.
- [x] Send throttled macOS notifications on meaningful failure-state transitions.
- [x] Add privacy-safe structured logging for run, protocol, and publication stages.
- [x] Export a redacted support bundle containing configuration shape, versions, and recent errors.

### P1 — Delivery latency implementation and remote-tree resource use

Goal: safely publish eligible newsroom files before a very large recursive scan completes.

- [x] Implement the completed-directory snapshot design in `2.7-Delivery-Latency-Design.md`.
- [x] Replace `Array.removeFirst()` tree-walker queues with indexed queues or deques.
- [x] Re-run the 100,000-file FTP/SFTP benchmark and record median and p95 changes.

Acceptance criteria:

- Early publication retains all output-ownership, path-collision, and atomic-publication guarantees.
- Large directory counts do not cause quadratic queue operations.

### P2 — Editing safety and application structure

- [x] Warn before switching jobs or closing a window with unsaved job edits.
- [x] Keep new jobs as drafts until their first successful save.
- [x] Split `MetadataProgrammingView`, `JobDetailEditor`, and the remaining `AppStore` responsibilities into focused components.
- [x] Add an optional content-integrity mode for equal-size, equal-timestamp files.

### P2 — Known server profiles

Goal: configure a remote server once and reuse it safely across multiple jobs and remote paths.

- [ ] Store named FTP, FTPS, and SFTP server profiles separately from jobs.
- [ ] Keep job-specific remote paths on job endpoints while referencing a shared server profile for protocol, host, port, username, credentials, and SFTP host-key trust.
- [ ] Migrate existing embedded remote endpoints into server profiles without changing job behavior or losing credentials.
- [ ] Commit server, job-reference, and Keychain changes transactionally.
- [ ] Show which jobs use a server before editing or deleting it, and prevent deletion while references remain.
- [ ] Allow users to duplicate a server profile when one job needs independent credentials or trust settings.
- [ ] Include referenced server profiles in configuration import/export without exposing passwords or creating broken references.
- [ ] Add migration, shared-edit, credential-failure, deletion-safety, and configuration-transfer regression coverage.

Acceptance criteria:

- Multiple jobs can reuse one server profile while selecting different remote paths.
- Editing a shared server clearly identifies and consistently updates every affected job.
- A failed save cannot leave jobs referencing a missing profile or mismatched Keychain credential.
- Existing saved jobs continue to work after automatic migration.

### P2 — Automated release coverage

- [ ] Add a macOS UI smoke-test target for job creation, editing, error recovery, and configuration transfer.
- [ ] Add local FTP, FTPS, and SFTP write/fault integration tests.
- [ ] Run the security baseline, vendored SSH signature tests, and application tests in CI.
- [ ] Refresh release wording in `SECURITY.md` and the configuration package type description.
