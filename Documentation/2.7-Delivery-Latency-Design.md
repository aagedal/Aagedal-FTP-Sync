# Aagedal FTP Sync 2.7 delivery-latency design

This document records the safety boundary for restoring early delivery and the benchmark needed to judge it. The current full-listing path remains authoritative until every invariant below is implemented and tested.

## Why the former fast-start path stays disabled

The former implementation chose a small batch from a partial recursive listing and published it before the source namespace was complete. A later source entry could therefore own the same output. For example, `SAME.CR2` and `SAME.NEF` both generate `SAME.xmp`; discovering one on each side of the batch boundary could overwrite or partially publish the pair.

Point-looking up a destination path is not enough. It does not prove that an undiscovered source path will not generate the same output, and a normal import after a successful lookup has a time-of-check/time-of-use race with other destination writers.

## Replacement: completed-directory snapshots

Replace `listFilesForFastStart` with a shared incremental tree walker used by both the early and full listing paths. It yields a directory only after that directory's listing is complete:

```swift
struct CompletedDirectoryListing: Sendable {
    let relativeDirectory: String
    let entries: [RemoteTreeEntry]
    let validatedAncestors: [String]
}
```

Before yielding, the walker must reject case- or Unicode-equivalent sibling names in the directory and in every already enumerated ancestor. This closes the namespace containing files in the completed directory even while unrelated descendant directories remain unscanned.

FTP and SFTP must use the same traversal policy so partial and complete scans cannot disagree about ordering or path validation. An FTP candidate must have an authoritative MDTM value when the recent-file filter or source-modification metadata scheduling depends on its timestamp; MDTM failure makes that candidate ineligible for early publication.

## Output ownership and atomic publication

For every eligible source file in a completed directory, build a `TransferOutputGroup` containing all paths the transfer may publish: the primary path, an existing XMP sidecar, and any generated XMP sidecar. Validate all groups in that directory together with the destination namespace before selecting a small newest-first delivery batch.

The local destination needs a conditional group-publication capability rather than a lookup followed by ordinary import:

1. Prepare every output in private sibling staging files.
2. Recheck that each expected destination path is still absent or still has the expected signature.
3. Commit the whole output group without replacing an unexpected file.
4. Roll back files already committed if a later member of the group cannot be published.

This makes a RAW/XMP pair one publication unit and closes the destination time-of-check/time-of-use race.

## Reconciliation with the full scan

Record early work as `[relativePath: SourceFileSignature]`, not only a set of paths. When the full listing reaches that path:

- Skip a matching signature without double-counting its transfer or metadata audit.
- Treat a changed signature as a fresh normal candidate.
- Keep cleanup and processed-source removal in the authoritative full-list phase.

The initial implementation scope should be one-way remote-to-local jobs with processed-source removal disabled. A failed full scan after a successful early publication must report the partial success explicitly; it must never claim an all-or-nothing run.

## Required regression coverage

- Safe files publish after their containing directory completes and before the recursive scan finishes.
- Same-stem RAW owners split across the former batch boundary publish nothing.
- Case- and Unicode-equivalent file or parent-directory names publish nothing.
- An existing destination collision, or a file created between validation and commit, is not overwritten.
- A failure publishing the second member of a RAW/XMP group rolls back the first.
- A source signature changed between the incremental and full snapshots is handled once as the final version.
- FTP MDTM failure prevents early publication when an authoritative timestamp is required.
- Cancellation and full-list failure preserve accurate transfer counts and audit entries.

## Resource-control policy implemented for 2.7

Whole sync and metadata-reprocessing runs acquire one shared concurrency lease before opening endpoint sessions. The app default admits at most two runs globally and one run per normalized remote `host:port`. The policy type also supports disabling the per-host limit for controlled tests or a future setting. Pending work is cancellation-safe and releases capacity when cancelled before admission.

The lease wraps the whole engine run, leaving the deliberate concurrent listing of a job's source, destination, and processed folder unchanged.

## Benchmark plan

Use two layers:

1. A deterministic tree-shaped fake scanner in the application tests. Record directory-call order, the first eligible snapshot, full-scan completion, and event ordering. These assertions are stable enough for CI.
2. An opt-in performance target backed by local FTP and SFTP services exposing the same fixed tree. Seed 100 directories × 10 subdirectories × 100 files, fixed sizes and timestamps, an early newest eligible file, and collision sentinels late in the tree.

Measure source full-scan time separately from end-to-end first-file publication. For each protocol and cold/warm state, run one warm-up plus five measured iterations and report median and p95 with the file count, tree shape, build configuration, and hardware. Absolute loopback timings are informational; correctness event ordering and request counts remain the CI gates.

The opt-in harness is `Scripts/run-delivery-latency-benchmark.py`. It seeds the fixed tree, starts read-only loopback FTP and SFTP services, runs `DeliveryLatencyBenchmarkTests`, and writes `2.7-Delivery-Latency-Benchmark.md`. Install its isolated Python dependencies and run it with:

```sh
python3 -m venv /tmp/aftpsync-benchmark-venv
/tmp/aftpsync-benchmark-venv/bin/python -m pip install \
  -r Scripts/delivery-latency-requirements.txt
/tmp/aftpsync-benchmark-venv/bin/python \
  Scripts/run-delivery-latency-benchmark.py
```

The September 1 baseline completed the planned 100,000-file, five-sample matrix. Median full scans were 10.362 seconds for cold FTP and 4.181 seconds for cold SFTP; median first publication was 15.693 seconds for cold FTP and 11.563 seconds for cold SFTP. These are measurements of the authoritative full-scan path, not the unimplemented completed-directory replacement. See `2.7-Delivery-Latency-Benchmark.md` for all warm/cold medians and p95 results.
