# Aagedal FTP Sync 2.8 Improvement Plan

This plan covers the next feature cycle after the 2.7.1 release. The working target is 2.8 because the scope combines a visible map workflow improvement with unattended-operation and data-safety work. If the final release contains only a narrow subset, it can still ship as 2.7.2.

Correctness and recoverability remain release blockers. Product and structural work should not weaken the existing transport, metadata, or rollback guarantees.

## P0 — Safe recovery of shared server profiles

Goal: never start an automatic job with server connection settings restored from an older backup until the user has reviewed them.

- [x] Propagate server-profile backup recovery as configuration recovery state.
- [x] Pause every affected automatic job at launch, as already happens after jobs-file recovery.
- [x] Explain which configuration was recovered and require an explicit restart.
- [x] Add regression coverage for each recovered FTP, FTPS, and SFTP profile type referenced by enabled jobs.

Acceptance criteria:

- A recovered profile cannot trigger an unattended upload or download.
- Jobs with unaffected configuration remain inspectable and can be restarted deliberately.
- Missing profiles continue to fail without attempting a connection.

## P0 — Bounded and cancellable SFTP operations

Goal: a connected but unresponsive SFTP server cannot leave a job permanently busy.

- [x] Add an inactivity deadline to listing, attributes, reads, writes, renames, and removals.
- [x] Close the SFTP/SSH channel when an operation times out or its owning task is cancelled.
- [x] Preserve an actionable timeout category in the failure history and structured log.
- [x] Add loopback fault tests for a server that accepts a connection and then stops replying.

Acceptance criteria:

- Stop Job releases the job and its concurrency lease promptly.
- Timed-out automatic jobs enter normal retry backoff.
- No partially published destination replaces a previous valid file.

## P1 — Photographer Map mini-timeline

Goal: show who is scheduled where and for how long while retaining fast time scrubbing on the map.

- [x] Replace the context-free slider with compact, per-day photographer lanes.
- [x] Draw scheduled clips at their real duration and distinguish clips with and without valid GPS positions.
- [x] Keep the timeline bound to the map time and retain previous/next location-change navigation.
- [x] Clip overnight assignments to the selected day and use that day's photographer-track order.
- [x] Add model-level regression coverage for row order, empty tracks, overnight clipping, and location state.
- [x] Add direct clip selection and double-click navigation to Metadata Programming after interaction testing.
- [x] Keep nearby photographer labels legible with deterministic screen-space collision avoidance and connector lines for displaced labels.

Acceptance criteria:

- Scrubbing any lane updates the map immediately.
- Pin colors and lane colors remain consistent.
- Nearby name labels avoid one another and visible pins when the map has room, without moving the underlying locations.
- The control stays compact with many photographers and remains adjustable with VoiceOver.
- Schedule edits remain owned by Metadata Programming; the map timeline is an overview.

## P1 — Safer job reset ownership

Goal: Reset Job removes app-owned downloads without relying on the user to notice that an ordinary destination may contain unrelated files.

- [x] Record a durable manifest of successfully published local paths.
- [x] Reset only manifest-owned paths, or require the managed `Synced Files` structure for whole-folder reset.
- [x] Preview the number and location of files before deletion.
- [x] Keep rollback behavior and clear history only after file removal succeeds.

Acceptance criteria:

- An unrelated file in an ordinary destination is never deleted by Reset Job.
- Reset remains recoverable when staging or final deletion fails.
- Existing jobs without a manifest receive a safe migration or a managed-folder-only reset path.

## P1 — Bounded source-signature storage

Goal: long-running newsroom jobs do not accumulate an indefinitely growing in-memory JSON database.

- [x] Replace whole-store JSON rewrites with an indexed SQLite or journaled store.
- [x] Prune records made irrelevant by authoritative source and destination state.
- [x] Define a conservative retention policy for paths whose source has been processed or temporarily disappeared.
- [x] Add scale tests for at least one million signature records and interrupted migrations.

Acceptance criteria:

- Lookup and batch persistence remain bounded as history grows.
- Pruning cannot cause metadata-transformed destinations to be retransferred incorrectly.
- Existing signature files migrate atomically and remain recoverable.

## P2 — Release identity and automation

- [x] Treat 2.7.1 as the latest shipped version and move later changelog entries under Unreleased.
- [x] Align the current project marketing version with the shipped 2.7.1 baseline.
- [ ] Decide between 2.7.2 and 2.8.0 before the first release candidate; prefer 2.8.0 if the map and hardening slices ship together.
- [ ] Add a release script that validates the project version, changelog heading, build number, and security-policy wording.
- [ ] Run remote transport tests in scheduled CI and add signed UI smoke coverage on an appropriate runner.

## P2 — Accessibility and localization

- [ ] Add an English string catalog and move user-visible strings into it as views are touched.
- [ ] Give every image-only action an explicit accessibility label and help text.
- [ ] Add VoiceOver-adjustable behavior and keyboard coverage for custom timeline controls.
- [ ] Audit truncation and contrast at accessibility text sizes.
