# FTP Sync 3.0 readiness

Status: IMPLEMENTING — routine version 3 launch is now streamlined: fresh installs
create an empty store silently, ordinary 2.9 installations receive one explicit upgrade
action, healthy committed stores reopen automatically, and technical source selection is
reserved for ambiguous/recovery inventories. Shared per-image template preparation is integrated into
preview, transfer and conditional local reprocessing. Explicit variable editors,
linked-calendar activation admission, an admitted AuraFace inference-runtime
foundation, injected recognition transfer/reprocessing paths and M5 durable processing receipts are
implemented; receipt-driven stale/incomplete reprocessing and output-edit preservation
are now selectable in the programming UI, with a no-write preflight and an explicit,
path-and-output-revision-bound action for reviewed edit conflicts. Version 3 startup can now locally admit
and bind a strictly configured immutable face context into preview, transfer and
reprocessing before either app writer is published, and later committed opens restore
only admitted jobs configured to start on launch. People Library settings now expose
the explicit signed-model download/install, cancellation, retry and removal lifecycle
when production trust is configured. Legacy no-write receipt bootstrap
requires durable prior source evidence. Native empty-store and isolated populated-store
startup now pass after correcting an App Sandbox lease failure. Signed damaged-primary
and interrupted-prepared recovery variants also pass. The nested-sheet accessibility
recursion is corrected, and the complete signed UI suite now passes 18 of 18 tests on
the current host without an app crash. SwiftMediaMetadata 3.0.1 is now pinned exactly
and passes the full app/UI regression plus metadata compatibility probe. Activated
workflows, live geocoding, production face identities/calibration and
candidate readiness remain incomplete. The focused signed save-failure UI test now
passes without its prior SwiftUI view-update warning, and the disposable PHP/MariaDB
release suite passes its hosting, live-sync and template-namespace checks. A one-way
server download can now derive its filename prefixes from the selected photographers
on the current Metadata Programming day, with an empty day selecting no files.

## Release-tier gap estimate

The plan defines final acceptance, not a separate beta gate. For a 3.0 beta that
exercises the declared feature scope, five substantial groups remain: (1) production
face-model trust, hosted signed artifacts and installer verification; (2) authorized
real-face calibration plus the companion export/import lifecycle; (3) native activated

images and RAW/XMP integrity; (4) actual protocol-3 calendar migration and older-

core regressions and macOS 14 smoke. The PHP/MariaDB suite is now passing; it does not
replace group 4's native integration. None of these five groups has complete acceptance
evidence yet. The app remains a 2.9.2 development build.

The new programming-derived server filename mode now passes a live FTP/FTPS/SFTP

all three transports; camera RAW, native UI and external-reader acceptance still
belong to group 3.

Final release additionally needs the complete M5 delivery/idempotence/rollback matrix,
controlled cold/warm enriched performance against M0 budgets, oldest/newest supported
macOS and native VoiceOver/localization evidence, the 41 required agent checklist cases
plus independent review, and M6 documentation/notices/versioned signed archive and the

authorized labeled fixtures and a macOS 14 test host are available, is 2–4 weeks to a
meaningful beta and 4–8 weeks total to a final user-test handoff. These are planning
ranges, not a release date; unavailable prerequisites can extend them.
