## Outcome and scope

Version 3.0 will enrich incoming pictures automatically with reusable metadata
templates, place names derived from GPS, and names matched against a local people
library. Aagedal Photo Agent supplies reusable processing code and the workflow
for maintaining reference faces.

The initial release includes:

- Variables in Headline, Description, Keywords, and photographer Copyright
  templates, with an insertion menu and a preview of resolved values.
- Automatic City and Country fields and location variables, using offline or
  explicitly selected online reverse geocoding.
- Automatic face matching against an imported Photo Agent Known People library,
  writing accepted names to Person Shown and optionally Keywords.
- Per-file results, recoverable failures, explicit reprocessing, and portable
  templates that survive configuration export and metadata calendar sharing.

Retain the current one-way, local-destination metadata boundary: remote-to-local
and local-to-local jobs. Automatic metadata on uploads and bidirectional jobs is
outside 3.0. All new processing options default off for existing jobs. Standalone
geocoding and face matching must work without an enabled schedule or matching
clip; scheduled text still requires the existing photographer/clip assignment.

Keep Apple silicon and macOS 14 as the compatibility target unless the initial
compatibility investigation demonstrates a blocker. A change to that product
target must be recorded before implementation proceeds on that assumption.

## Product behavior

### Variables

Use Photo Agent's existing spellings where available and add `{photographer}`.
The insertion menu should offer capture date first for captions.

| Variable | Meaning | Example |
| --- | --- | --- |
| `{gps:city}` | City resolved from the effective image coordinates | `Oslo` |
| `{gps:country}` | Country resolved using the chosen place-name language | `Norway` |
| `{dateCaptured:YYYY-MM-DD}` | EXIF original capture date, including its offset when present | `2026-09-09` |
| `{date:YYYY-MM-DD}` | Processing date in the job's configured time zone | `2026-09-09` |
| `{photographer}` | Matched profile's canonical Creator/display name | `Truls Aagedal` |
| `{persons}` | Existing Person Shown names merged with accepted recognition results | `Example Person` |

`{persons}` is delivered with the face-recognition milestone. General field
references, sequence numbers, filename expansion, arbitrary expressions, and a
complete copy of Photo Agent's variable catalog are deferred.

Example Description template:

```text
{gps:city}, {gps:country}, {dateCaptured:YYYY-MM-DD}. Photo: {photographer}.
```

Resolved for one example picture:

```text
Oslo, Norway, 2026-09-09. Photo: Truls Aagedal.
```

Rules:

- Persist the original template. Resolve it separately for each picture when
  preparing metadata, never when saving a preset or copying a timeline clip.
- Store an explicit template-language version/activation marker alongside each
  template-bearing record. Legacy strings remain literal until variable
  processing is explicitly enabled; upgrading must not reinterpret old braces.
- Start with the documented `YYYY-MM-DD` format and accept `yyyy-MM-dd` as its
  equivalent. Translate the friendly spelling to calendar-year formatting
  internally; do not use week-based year `YYYY` or day-of-year `DD` directly.
- Use a fixed Gregorian calendar and numeric formatting. Preserve the capture
  date's explicit offset; when EXIF has no offset, use a persisted job time zone
  initialized from the Mac's setting. Never silently substitute today's date for
  missing capture metadata. Show the assumed time zone in preview/audit details.
- Capture processing time once for the item's operation, sharing it between
  fields and retries within that operation. An explicit later reprocess may
  resolve a new processing date and must show that change in its preview.
- `{photographer}` uses `PhotographerProfile.photographerName`, including its
  existing legacy-name fallback. It is independent of Person Shown. Resolve it
  from the matched profile before expanding Copyright to avoid self-reference.
- Resolve only supported tokens, once. Substituted text is literal, even if it
  contains braces. Define `{{` and `}}` as literal-brace escapes and validate
  unknown tokens, unsupported formats, unmatched braces, and excessive input.
- Normalize and deduplicate Keywords after expansion. Each keyword template
  remains one entry; commas inside a resolved value must not create accidental
  extra keywords. Face-to-keyword insertion adds each name as a separate entry.
- An unavailable variable suppresses the entire affected field, preserving its
  existing metadata. For Keywords, preserve the existing list if any template
  entry cannot resolve; separately accepted face names may still be appended.
  Other fields may apply. Never publish unresolved tokens or silently remove
  words from a caption.
- Preview reports missing values and shows the final proposed text alongside
  existing values and preservation decisions. Unknown syntax prevents activation
  of the affected template; drafts remain editable.

### Reverse geocoding

- Provide independent per-job options for resolving place variables and writing
  City/Country. A location token must declare its geocoding dependency in the
  editor; disabling lookups must show that the template cannot resolve.
- Default to offline GeoNames through SwiftMediaMetadata. Expose place-name
  language and an online Apple option. Explain that online lookup sends
  coordinates to Apple; offline lookup stays on the Mac.
- Resolve the effective coordinate pair after applying the current scheduled GPS
  preserve/overwrite policy. For RAW, honor a valid existing XMP pair before
  embedded EXIF. For embedded images, retain the writer's EXIF-first precedence
  and use XMP as fallback. Record conflicting valid pairs; never combine latitude
  from one source with longitude from another. A valid scheduled replacement
  supersedes the pair only when the existing policy permits it.
- Resolve once per distinct coordinate pair, engine, dataset/provider version,
  and concrete output locale. Coalesce concurrent identical requests and bound
  cache size/retention. Avoid coarse spatial rounding that can cross borders.
- Geocoded variables use the lookup result. City and Country field writes
  independently obey fill-empty/overwrite rules, so preserving an existing city
  does not silently change the meaning of `{gps:city}`.
- The offline database finds a nearby city, not a street address or a verified
  administrative boundary. Retain distance and source in the internal result;
  define a maximum-distance policy and include rural/coastal/border examples in
  validation. Do not promise exact venue names or localized offline city names.
- Missing/invalid GPS, no result, timeout, or provider failure leave affected
  metadata unchanged and produce a specific outcome. Do not silently switch
  providers or languages; make retries and any future fallback policy explicit.
- Online requests use a shared bounded queue, caching, cancellation, finite
  deadlines, and backoff. Photo Agent's batch delay is not a throughput guarantee.

### Face recognition and the people library

- Detect faces locally, compute AuraFace embeddings, and compare them only
  against the selected imported people library. Photo Agent remains the reference
  face editor; FTP Sync initially provides import, library summary, replacement,
  and removal rather than a new face-training interface.
- Treat an import as a validated library snapshot. Replacing that snapshot
  reflects renamed/removed people and updated examples; do not copy Photo Agent's
  current import behavior that only adds previously unseen person UUIDs.
- Define a versioned interchange manifest containing the embedding-space version,
  model identifier, preprocessing revision, vector encoding/dimension, and library
  identity/revision. The inspected Photo Agent ZIP manifest has a general version
  and counts but does not explicitly bind the embedding space. Coordinate an
  exporter update there; accept older exports only when compatibility can be
  demonstrated, otherwise request a compatible re-export without changing data.
- Preserve Photo Agent editor-only metadata in a hash-bound optional payload when
  importing and re-exporting a people library. FTP Sync validates its binding but
  treats private source descriptions as opaque. Keep Photo Agent as the sole editor.
  Automatic local synchronization, if enabled later, uses one immutable pointer in
  an opt-in shared App Group; neither app reads the other's private storage.
- Do not treat legacy Photo Agent Known People archives as AuraFace v3 evidence.
  Require durable model/preprocessing provenance or explicit re-enrollment before a
  companion export can claim compatibility with the schema-2 embedding contract.
- Validate archive paths, symlinks, sizes/counts, duplicate IDs, vector dimensions,
  finite values, codec versions, and thumbnail formats before atomic installation.
  Keep the previous library usable after a failed or interrupted import.
- Hold an immutable library/model snapshot for a processing operation. Imported
  names are data and must not be interpreted as template syntax.
- Reuse face alignment, quality filtering, embedding normalization, similarity
  scoring, and the best-versus-runner-up ambiguity guard. Calibrate thresholds
  specifically for unattended single-image delivery; grouping thresholds are
  not automatically suitable for publishing identities.
- The current score is derived from cosine distance, not a calibrated probability.
  Do not present it as a percentage likelihood of identity. No match, uncertain
  match, and insufficient face quality are distinct normal outcomes.
- Preserve existing Person Shown names and append accepted names once in a stable
  order. Optional Keywords insertion follows the same append/deduplicate rule
  after scheduled keyword policy has been applied. Never infer the photographer
  from a detected face or auto-enroll uncertain matches as reference examples.
- Keep reference thumbnails/embeddings out of normal `.aftpsync` exports, calendar
  sharing, ordinary logs, and default support bundles. Store the library in app
  support, with no `.faces` directories created in incoming folders.
- Use Photo Agent's optional verified model-installation design. The documented
  component is approximately 125 MB and works locally after installation. Recheck
  hosted artifacts, signing-key configuration, model compatibility, notices, and
  removal behavior; production availability is not established by this plan.
- A missing or incompatible model/library disables face processing with an
  actionable status while file transfer remains available. Recognition errors
  preserve existing names and leave dependent `{persons}` templates unresolved
  when no usable names remain.

### Processing pipeline

Introduce a `MetadataProcessingCoordinator` with an optional schedule assignment
and independent geocoding/recognition settings. Its output is a resolved metadata
change set plus field/stage outcomes, not a mutated stored template.

1. Stage the source image and any existing RAW/XMP companion using current transfer
   validation. Read original metadata and freeze the operation's settings, time,
   source identity, template revision, and model/library revision.
2. Find the photographer and optional schedule clip. Construct proposed static
   metadata changes and resolve the effective GPS pair in memory.
3. Determine which fields are writable under their policies and which variables
   they need. Avoid expensive work for fields that will be preserved and for
   disabled features. Honor standalone City/Country and Person Shown requests.
4. Resolve required place names and face matches through their bounded services.
   Build the complete immutable variable context, including merged Person Shown.
5. Expand eligible templates, validate/deduplicate final values, and assess actual
   changes. Preserve fields with missing dependencies and collect their outcomes.
6. Write once to the private working image or XMP sidecar through `MetadataWriter`.
   Preserve unrelated metadata and RAW bytes. Publish using the existing output
   group transaction, timestamp policy, verification, and rollback paths.
7. Persist successful processing provenance with destination ownership and source
   signatures. Emit transfer and metadata outcomes separately; a metadata omission
   must not be reported as complete enrichment.

Primary integration points:

- [MetadataAutomation.swift](../AagedalFTPSync/Models/MetadataAutomation.swift):
  template activation/versioning, writable fields, settings, and assignment context.
- [SyncJob.swift](../AagedalFTPSync/Models/SyncJob.swift): independent processing
  eligibility and validation, preserving current endpoint/direction restrictions.
- [MetadataWriter.swift](../AagedalFTPSync/Metadata/MetadataWriter.swift): typed
  resolved changes, City/Country/Person Shown, and embedded/sidecar parity.
- [SyncEngine.swift](../AagedalFTPSync/Sync/SyncEngine.swift): normal transfer,
  completed-directory early delivery, reprocessing, possible sidecar reservation,
  metadata-modified destination comparisons, and processed-file handoff.
- [MetadataPreview.swift](../AagedalFTPSync/Metadata/MetadataPreview.swift): move
  from assignment-only checks to asynchronous, cancellable resolution with the
  same coordinator and visible proposed values; source files stay read-only.
- [MetadataAudit.swift](../AagedalFTPSync/Models/MetadataAudit.swift): field/stage
  results and partial completion, compatible with older saved audit records.

### Delivery, failure, and reprocessing rules

- Keep final metadata ready before publishing the visible output. Enrichment may
  delay an enabled job; do not modify files after downstream watchers see them.
- Use a bounded inference worker, initially one image at a time, plus a separate
  geocoder queue. Limit pending work by count and staged bytes. Preserve existing
  transport scheduling and cancellation; measure the impact of holding a job lease
  during inference before adding more concurrency.
- Core ML work already executing may not be interruptible. Check cancellation
  around it, stop admitting more images, and prevent a late result from publishing.
  Provider deadlines, queue limits, and measured cancellation latency are explicit
  outputs of the compatibility/performance investigation.
- A lookup/model failure may still deliver the image with other successfully
  resolved fields. A metadata write failure falls back to the intact original
  image/sidecar, following existing recovery behavior. Publication failures retain
  the existing transaction rollback guarantees.
- Block processed-source removal when requested enrichment has unresolved values
  or failed stages. Successful scanning with no faces or no accepted matches is a
  completed stage; a dependent caption that cannot resolve remains incomplete.
  Keep existing source comparison, output verification, and collision checks.
- Preserve source signatures as source evidence, separate from output metadata.
  Face/geocode-only jobs must also reserve generated sidecars and identify outputs
  as metadata-transformed; do not key those paths only on a schedule assignment.
- Record a processing fingerprint from source/companion evidence, template and
  policy revisions, locale/time-zone assumptions, and model/library versions.
  Record output signatures and the processing date used. This supplements the
  source-signature store; it does not reinterpret its size/date evidence as a hash.
- Polling an unchanged source never re-expands `{date}`, rescans faces, or rewrites
  an unchanged result. Model/library/settings updates make prior processing stale
  for explicit reprocessing, not automatic retransfers of the entire folder.
- Offer filtered reprocessing for incomplete/stale results. Freeze a fresh context,
  preview intended changes, and reject writes if the destination changed after it
  was read. On restart, discard temporary partial work and retain the last
  successfully published state. Do not promise rollback of names already sent to
  other systems when a library entry is later renamed or removed.

## Persistence, exports, and shared calendars

- Decode old jobs, presets, photographer records, audit entries, and signature
  stores without enabling any new processing. Empty/removed calendars must not
  disable independently enabled geocoding or face recognition.
- Define an explicit local downgrade boundary. If older binaries cannot reject
  template-enabled storage, migrate affected stores to versioned 3.0 paths and
  retain a consistent 2.9 backup. Do not let an older installation reinterpret or
  overwrite new templates; document that returning to 2.9 restores older settings.
- Keep template source and its language/activation marker together through copy,
  paste, preset application, full and selected-day exports, conflict resolution,
  and calendar merges. Resolve using each image, never the editor's sample values.
- Extend `ConfigurationTransfer` with a format version that older clients reject
  for template-enabled data. Continue accepting versions 1 and 2; export legacy
  compatible packages only when no unsupported processing semantics are present.
- Calendar sharing is a release gate: the current protocol is version 2 and older
  clients understand ordinary strings. Add protocol/capability negotiation and
  enforce it on the server for calendars using templates. Audit cached offline
  calendars too: a server rejection cannot retract template strings already saved
  by an older client. Unsupported clients must never receive template-bearing
  documents in the first place or upload downgraded versions that lose markers.
- Preserve sharing for legacy calendars. If the installed server cannot enforce
  the new contract, prevent publishing/activating variables on that shared calendar
  with a clear upgrade message; local templates can still work. Add the capability
  to shared template/profile records without sharing machine processing policies.
- Store language/provider choice, time-zone fallback, thresholds, library binding,
  and model installation locally. Ordinary configuration exports may carry portable
  job policies but not model files, private library contents, or machine paths.
  Imported jobs remain disabled and require local library/model setup as needed.

## Planning deliverable

This change records the design and implementation sequence only. No application
version, dependency, server protocol, model installation, or runtime processing
behavior is changed by the planning work.
