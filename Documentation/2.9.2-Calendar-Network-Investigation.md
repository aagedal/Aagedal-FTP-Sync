# Calendar network errors reported against 2.9.2

Investigated 2026-09-09 against stable source `a1d8f37`, with the implementation
checkout at `23fc3ab`. The changes in this report are an unreleased, independently
committed maintenance fix; they do not implement a 3.0 feature or change the version.

## Evidence and limits

The supplied sanitized diagnostics show URL errors -1004 (connection to host failed),
-1001 (request timeout), and -1009 (the URL loading system reports no internet connection).
Several later entries explicitly report recovery and current revision 18. Most -1004
entries concern the calendar list, which is distinct from an individual calendar's
content. Successes for routine list/fetch requests are intentionally not all logged.
Therefore counts of error entries cannot be interpreted as a percentage of failed syncs.

The excerpt cannot distinguish hosting availability, local connectivity, network
transitions, VPN/proxy interference, or a connection-path problem. No live endpoint
was contacted, no production credentials were read, and no claim is made that retry
handling fixes the underlying network condition. No calendar corruption is established
by this excerpt. The response to the user requests context about concurrent internet
access and sleep/network changes.

## Confirmed client issues and changes

Before: a full refresh every ten seconds listed calendars, attempted linked calendar
fetches even after the account connection failed, and recorded the same fetch error
again at the outer sync layer. Alternating events also defeated adjacent-event grouping.

After:

- Automatic connection-failure retries use per-account waits of 10, 20, 40, 80, 160,
  then at most 300 seconds, measured after the failed pass. Normal polling resumes
  after a successful pass. Local edits stay durable during cooldown.
- The first connection failure skips remaining requests for that account in that pass.
  Other accounts are still eligible. Validation/server-content errors are not treated
  as connection outages.
- Explicit refresh/Retry Now bypasses cooldown, including when queued behind automatic
  work. Saved-edit and polling requests respect cooldown.
- Background calendar discovery runs at most once a minute after a successful listing.
  Linked calendar updates keep their normal ten-second cadence while reachable.
  Selecting an account invalidates its cleared picker list so it can reload promptly.
- Network request diagnostics are recorded once and include a fixed human-readable
  explanation plus the URL code. Raw error text, URLs and credentials stay excluded.

Tradeoff: after repeated outages automatic recovery may wait up to five minutes after
connectivity returns; Retry Now bypasses that wait. No reachability monitor is added.

## Verification

An independent reviewer checked backoff scope, queue intent, saved edits and diagnostics,
and identified the account-switch invalidation issue, which was fixed before final tests.

The complete macOS unit suite passed:

```sh
xcodebuild test -project 'Aagedal FTP Sync.xcodeproj' \
  -scheme AagedalFTPSync -destination 'platform=macOS' CODE_SIGNING_ALLOWED=NO
```

488 discovered tests: 473 passed, 15 opt-in/environment-dependent tests skipped,
zero failures. Log: `/tmp/ftp-sync-network-full-tests.log` (temporary local evidence).
New regression cases cover redundant offline requests, increasing retry delays,
manual bypass and recovery, healthy discovery cadence, account selection, mixed queued
manual/automatic requests, single error recording, and saved edits during cooldown.
The existing calendar merge, lost-response, persistence, rapid-edit, draft and queued
refresh regression tests also passed. No signed UI, real server, or user-network test
is claimed by this run. Installed 2.9.2 is unchanged until a new build is installed.
