# Aagedal FTP Sync 2.5 Metadata Roadmap

## Goal

Automatically apply editorial metadata to incoming images on a per-job basis. One or more filename initials identify the photographer, while a scheduled clip selects the event metadata that is valid at the file's timestamp.

## Phase 1 — Safe end-to-end foundation

Status: implemented in the initial 2.5 work.

- Store photographer profiles and metadata schedules inside each sync job.
- Match one or more comma-separated prefixes per photographer case-insensitively against the filename, independent of folders and extensions.
- Use half-open clip ranges (`start <= timestamp < end`) so adjacent clips have an unambiguous boundary.
- Apply non-empty Headline, Description, Keywords, Creator, and Copyright values through SwiftMediaMetadata during transfers to a local destination, preserving fields that were left blank in the programming UI.
- Synchronize IPTC values into XMP.
- Preserve the source modification time and avoid retransferring files solely because embedded metadata changed their size.
- Add validation for duplicate prefixes, orphaned clips, invalid ranges, and overlapping clips on one photographer track.
- Provide a separate programming window reachable from both job settings and the menu-bar window.
- Provide a calendar, persistent photographer library, visual day tracks, clip editing, cross-day confirmation, and copying to another photographer.

## Phase 2 — Direct timeline editing

Status: implemented.

- Drag clips along the timeline and snap to configurable intervals.
- Drag across empty space on a photographer track to create a clip at that time, then double-click it to edit its metadata.
- Resize either edge, with explicit confirmation when a resize crosses midnight.
- Add multi-select and copy/paste across several photographer tracks.
- Highlight schedule gaps, overlaps, the current time, and clips that continue from another day.
- Add keyboard navigation and shortcuts for fast newsroom programming.

## Phase 3 — Metadata policies and RAW workflow

Status: implemented.

- Let each job choose whether scheduling uses source modification time, local arrival time, or camera capture time from Exif. Implemented; source modification time is the default, while camera capture and local arrival remain user-selectable. Files without a valid Exif capture time are transferred without scheduled metadata when that policy is selected.
- Preserve existing Headline, Description, Keywords, Creator, and Copyright values by default, filling only empty fields; provide an “Always overwrite” job option for non-empty programmed values. Implemented; previously saved programming retains its earlier overwrite behavior.
- Add XMP-sidecar output as the default for RAW formats, including DNG and CR3. Implemented; RAW image data is transferred unchanged and programmed metadata is written to a companion `.xmp` file.
- Keep timeline clips standalone, while allowing their metadata values to be saved to and quickly loaded from a reusable preset library shared across jobs and days. Implemented; presets have independent, backup-protected storage and loading one copies only its metadata values into the clip.
- Add an explicit “reprocess existing local files” action. Programming changes affect only newly transferred files unless the user invokes this action. Implemented for source-modification and camera-capture scheduling, with all-file, single-photographer, and single-clip scopes, confirmation, atomic local replacement, preserved modification dates, and RAW sidecar support. Local-arrival reprocessing is rejected because historical arrival timestamps were not recorded.

## Phase 4 — Operations and confidence

Status: implemented.

- Report metadata-applied, skipped, and failed counts separately from transfer counts. Implemented in each sync result, scheduled-run status, and reprocessing result.
- Keep a per-file audit trail containing the matched photographer, clip, timestamp policy, and SwiftMediaMetadata warnings. Implemented with bounded, backup-protected persistence and an expandable trail in job settings; skipped and failed decisions retain diagnostic details.
- Persist the original source signature so size verification can still detect an unusual source change that keeps the same modification timestamp after metadata has changed the destination size. Implemented per job, source endpoint, and relative path, including when destination dates are not preserved.
- Add dry-run preview for a local folder before enabling automation. Implemented from the metadata-programming window using the unsaved draft, with per-file assignment and skip reasons and no file writes.
- Add fixtures and round-trip tests for JPEG, TIFF, DNG, CR3, HEIC, and XMP sidecars. Implemented across local integration and metadata recovery tests; HEIC editorial fields are verified in its XMP metadata item because HEIF has no IPTC-IIM segment.
- Add recovery behavior for partial failures so a metadata error cannot leave a damaged destination file. Implemented by applying metadata to a separate working copy, falling back to the untouched downloaded file during sync, and retaining atomic destination replacement for sync and reprocessing.
- Add an opt-in processed-folder handoff per job. Implemented for one-way jobs with automatic metadata: the metadata-written file and any generated RAW sidecar are verified in both the destination and a separate local processed folder before the original is removed from a local, FTP, FTPS, or SFTP source. Skips, failures, and collisions retain the source.

## Product decisions

1. Resolved: source modification time is the default because it is available for every transferred file. Each job can select camera capture or local arrival time instead.
2. Resolved: preserve existing values and fill empty fields by default, with an option to always overwrite fields for which programming provides a value.
3. Resolved: use XMP sidecars for RAW files, including DNG and CR3.
4. Resolved: timeline clips remain standalone and contain their own values. A reusable preset library provides quick save/load without making clips depend on presets.
5. Resolved: programming changes affect new files by default; reprocessing existing local files is an explicit on-demand action.
